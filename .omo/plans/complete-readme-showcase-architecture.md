# complete-readme-showcase-architecture - Work Plan

## TL;DR (For humans)

**What you'll get:** A resumable, evidence-driven README pipeline that scans safely, produces traceable claims and previews, evaluates deterministic quality signals, prepares an approved pull request in an isolated worktree, and learns from local outcome data.

**Why this approach:** Each immutable run is bound to exact inputs and hashes, while compatibility wrappers keep today's commands working. Security and contract failures stop immediately; bounded scan limits preserve safe partial evidence, and content issues are returned together for efficient revision.

**What it will NOT do:** It will not call a model API, perform a real GitHub write during verification, execute arbitrary README commands, add YAML/config or Markdown-rendering dependencies, or alter the pinned ELK/motion supply chain.

**Effort:** XL
**Risk:** High - cross-cutting v1/v2 contracts, security boundaries, resumability, packaging, and delivery authorization must evolve without weakening 89-test compatibility baseline.
**Decisions to sanity-check:** Immutable attempt retention, restricted locale set, advisory-only feedback influence, and dry-run-only real `gh` verification are deliberate limits.

### Must NOT have (guardrails, anti-slop, scope boundaries)

- No real GitHub branch, commit, push, PR, permission-changing, or other remote write in implementation QA; no model/provider API or arbitrary candidate/README command execution.
- No YAML parser/config, Markdown renderer, LLM judge/report schema, vector database, cloud database/service, web admin UI, connector abstraction for one `gh` transport, or new runtime dependency.
- No weakening of path traversal, symlink, special-file, secret, hash, Git base/index/worktree, SVG, claim evidence, approval, remote permission, or split-leak fail-closed behavior.
- No ELK upgrade, lockfile churn, SRI/source-commit/image-digest change, motion pipeline redesign, renderer plugin system, or edits to generated README/media content beyond verification fixtures.
- No overwrite of immutable attempt directories, no timestamps in artifact fingerprints, no secrets/file bodies in manifests or logs, and no preview files in PR candidates.

## Verification strategy

> Zero human intervention - all verification is agent-executed.

- Test decision: TDD with stdlib `unittest`; every todo starts by pinning `git rev-parse HEAD^{tree}` and running its named existing baseline, then adds the smallest failing RED test/fixture before product code. Baseline is 89 discovered tests on Python 3.11 and 3.13; task work may increase count but never reduce coverage.
- Evidence root: no active attempt exists at planning time, so every task writes non-empty `.omo/evidence/task-N-pin.txt`, `.omo/evidence/task-N-red.txt`, `.omo/evidence/task-N-happy.*`, `.omo/evidence/task-N-failure.*`, `.omo/evidence/task-N-cleanup.txt`, and `.omo/evidence/task-N-commit.txt`; final gates use `.omo/evidence/task-FN-*`. If execution starts an ULW attempt, replace only the root with its reported `currentAttemptDir` while preserving each exact basename.
- Every artifact receipt records command, cwd, exit code, stdout/stderr digest, `git rev-parse --short HEAD^{tree}`, and assertions. A log saying “pass” without the named binary/data assertion is rejected.
- Milestone/full gates: `PYTHONDONTWRITEBYTECODE=1 python -m unittest discover -s tests -v`, targeted Python 3.10/3.11/3.12/3.13 CI equivalents, `npm test`, `npm pack --dry-run`, installer test, README audits, ELK vendor parity and real no-network render, motion render, `git diff --check`, process-residue scan, and dirty-worktree comparison.
- Security/adversarial fixtures use only OS temporary directories outside the repository, are deleted after each scenario, and must prove no repository/index mutation and no residual Python/Node/ffmpeg/rsvg/git-worktree processes or temp worktrees.
